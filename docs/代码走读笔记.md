## 1. 入口：`evaluate_dataset`

**位置**：`test_advanced_robust.py:174-329`

### 在干什么

一个 `for sample` 外层循环 + 一个 `for qa` 内层循环，中间夹着缓存判断。

```python
for sample_idx, sample in enumerate(samples):
    agent = RobustAdvancedMemAgent(model, backend, retrieve_k, temperature_c5, ...)

    memory_cache_file = os.path.join(memories_dir, f"memory_cache_sample_{sample_idx}.pkl")

    if os.path.exists(memory_cache_file):
        # 命中缓存：直接反序列化记忆 + 检索器
        with open(memory_cache_file, 'rb') as f:
            cached_memories = pickle.load(f)
        agent.memory_system.memories = cached_memories
        agent.memory_system.retriever = agent.memory_system.retriever.load(
            retriever_cache_file, retriever_cache_embeddings_file
        )
    else:
        # 未命中：逐轮灌记忆
        for _, turns in sample.conversation.sessions.items():
            for turn in turns.turns:
                conversation_tmp = "Speaker " + turn.speaker + "says : " + turn.text
                agent.add_memory(conversation_tmp, time=turns.date_time)

        with open(memory_cache_file, 'wb') as f:
            pickle.dump(agent.memory_system.memories, f)
        agent.memory_system.retriever.save(retriever_cache_file, retriever_cache_embeddings_file)
```

### 三个容易误解的点

1. **`ratio` 切的是对话数，不是题数。** `samples = samples[:max(1, int(10*ratio))]`，`ratio=0.1` 等于 1 个完整对话（588 轮）。想少跑题得改代码，改 `ratio` 没用。

2. **缓存按 `sample_idx` 命名，不按模型配置区分目录外的参数。** 缓存目录名是 `cached_memories_robust_{backend}_{model}`，**不含 `retrieve_k`**——这正是"换 k 只重跑答题"能成立的原因。但也意味着：你要是改了 prompt 或换了记忆逻辑再跑，旧缓存会被复用，结果不反映新代码。**改完核心逻辑必须手动删缓存目录。**

3. **`pickle` 存的是整个 `memories` 字典。** 反序列化要求 `RobustMemoryNote` 类能被 import 到。所以缓存文件跟代码强绑定，类结构一改就读不出来。

### 一句话记住

缓存按样本切、按「后端+模型」隔离；`ratio` 控制样本数而不是题量。

## 2. 灌记忆：`add_note` + `RobustMemoryNote`

**位置**：`memory_layer_robust.py:276-315`（构造函数）、`377-397`（add_note）

### 在干什么

```python
def add_note(self, content: str, time: str = None, **kwargs) -> str:
    note = RobustMemoryNote(
        content=content,
        llm_controller=self.llm_controller,   # 传了 controller → 构造函数里会调 LLM
        timestamp=time,
        **kwargs,
    )
    evo_label, note = self.process_memory(note)   # 先演化
    self.memories[note.id] = note                 # 再入库
    self.retriever.add_documents([                # 最后进向量库
        "content:" + note.content +
        " context:" + note.context +
        " keywords: " + ", ".join(note.keywords) +
        " tags: " + ", ".join(note.tags)
    ])
    if evo_label:
        self.evo_cnt += 1
        if self.evo_cnt % self.evo_threshold == 0:   # 默认 100
            self.consolidate_memories()
    return note.id
```

### 三个关键设计

1. **单条记忆存 7 个字段**：`content`（原文）、`keywords`、`tags`、`context`、`links`（邻居下标）、`timestamp`、`id`。前四个里除 `content` 外全由 LLM 分析生成。

2. **入库顺序 = 索引顺序。** `self.memories` 是 dict（Python 3.7+ 保序），`retriever` 是 list。代码所有地方都用 `list(self.memories.values())[i]` 反查，所以**两个容器的插入顺序必须严格一致**。`add_note` 里先 `memories[id]=note` 再 `add_documents`，顺序是对上的。

3. **检索文本是拼接后的富文本**，不是原文。向量库看到的是 `content: ... context: ... keywords: ... tags: ...`，所以关键词和标签会实质影响召回。

### 一个可以不管的小问题

构造函数里：

```python
if llm_controller and any(p is None for p in [keywords, context, category, tags]):
    analysis = self.analyze_content(content, llm_controller)
    keywords = keywords or analysis["keywords"]
    context  = context  or analysis["context"]
    tags     = tags     or analysis["tags"]
```

`category` 参与了"要不要调用 LLM"的判断，但**分析结果里根本没有 category 字段**，也从未被赋值。所以如果只传了 `keywords/context/tags` 而 `category=None`，会白发一次 LLM 请求。评测路径上四个参数都是 `None`，所以每次都调，不影响结果。

另外 `importance_score` 和 `retrieval_count` 两个字段**定义了但全代码从未使用**，是原版遗留的死字段。

### 一句话记住

一条记忆 = 原文 + LLM 生成的三个属性；入库顺序决定了下标对齐。

## 3. 检索：`find_related_memories_raw`

**位置**：`memory_layer_robust.py:430-459`

### 在干什么

```python
indices = self.retriever.search(query, k)
all_memories = list(self.memories.values())
for i in indices:
    memory_str += "talk start time:" + all_memories[i].timestamp + ...   # 先拼命中的这条
    neighborhood = all_memories[i].links                                # 再拼它的邻居
    for neighbor in neighborhood:
        memory_str += "talk start time:" + all_memories[neighbor].timestamp + ...
        if j >= k:
            break
        j += 1
```

### 两个细节

1. **实际拼进来的记忆远多于 k。** k 条命中，每条再挂自己 `links` 里的邻居，最多 `k + 1` 个。`logs` 里看到的 `Raw Context` 长度就是这么来的。

2. **`if j >= k: break` 写在拼接之后**，所以邻居循环会多拼一条（j 从 0 到 k，共 k+1 条）。这是个 off-by-one，但影响很小——context 多一两百 token 而已，不必修。

另一个隐含前提：**没有任何去重**。k 条命中之间如果互为邻居，同一段对话会在 context 里出现两三次。浪费 token，但不会算错。

### 为什么要有邻居扩展

因为 LoCoMo 的答案常需要多跳：命中的那条记忆可能只提到"8 May 的慈善跑"，而答案"她的脚受伤了"在相邻那一轮。邻居扩展就是补这个的。这也是 `process_memory` 要维护 `links` 的原因——**演化阶段建立的连接，在检索阶段被消费**。

### 一句话记住

检索 = top-k 命中 + 各自的邻居，不去重、会膨胀。

## 4. 演化：`process_memory`

**位置**：`memory_layer_robust.py:463-540`

这是 A-Mem 区别于普通 RAG 的地方，也是最值得细读的一段。

### 在干什么

```python
neighbor_memory, indices = self.find_related_memories(note.content, k=5)
if len(indices) == 0:
    return False, note                      # 库里没东西 → 不演化，直接入库

# ── 第 1 次调用：决策 ──
decision_response = self.llm_controller.llm.get_completion(decision_prompt)
decision = parse_evolution_decision(decision_response)
if decision["decision"] == "NO_EVOLUTION":
    return False, note

should_strengthen = decision["decision"] in ("STRENGTHEN", "STRENGTHEN_AND_UPDATE")
should_update     = decision["decision"] in ("UPDATE_NEIGHBOR", "STRENGTHEN_AND_UPDATE")

# ── 第 2 次调用：强化自己（条件触发）──
if should_strengthen:
    note.links.extend(strengthen["connections"])
    if strengthen["tags"]:
        note.tags = strengthen["tags"]

# ── 第 3 次调用：改邻居（条件触发）──
if should_update:
    noteslist = list(self.memories.values())
    for i in range(min(len(indices), len(neighbor_updates))):
        notetmp = noteslist[indices[i]]
        if upd["tags"]:    notetmp.tags = upd["tags"]
        if upd["context"]: notetmp.context = upd["context"]
```

### 四个要点

1. **三次调用是条件触发的，不是每次都 3 次。** 实际分布大致是：约一半走 `NO_EVOLUTION`（1 次调用结束），剩下的走 2 次或 3 次。算成本时按平均 2 次估比较准。

2. **第一条记忆永远不演化。** `if len(indices) == 0: return False, note`——库里空的时候检索结果为空。所以每个对话的第一轮必然跳过演化。

3. **`should_update` 分支在改的是"邻居"，不是新记忆。** 这是最容易看反的地方：A-Mem 的假设是"新记忆的到来会让我们重新理解旧记忆"，所以它回头去改老记忆的 `context` 和 `tags`。改完之后，同一段历史对话在不同时刻的标签是**会变的**——这既是特色，也是它难以复现的原因。

4. **失败不阻断。** 整个 try 包住，`except` 里 `return False, note`，新记忆照常入库、只是没演化。所以日志里出现零星的 `Evolution failed` 属正常，占比高才说明模型不行。

### 一个必须注意的副作用

`should_update` 阶段需要 `indices` 做下标。而 `indices` 是**检索发生时**算出来的，基于当时不含新记忆的 `self.memories`。到第 3 次调用时，`noteslist` 也是不含新记忆的列表（因为 `add_note` 是在 `process_memory` 返回之后才入库）。

**两边一致，所以这里没有错位 bug。** 但如果谁把 `self.memories[note.id] = note` 挪到 `process_memory` 之前，立刻就会下标错位、改错记忆。这是个很脆的设计，读的时候留意一下顺序。

### 一句话记住

新记忆进来 → 找 5 个邻居 → 决定是否强化自己 / 回头改邻居的标签和上下文。

## 5. 打分：`calculate_metrics`

**位置**：`utils.py:109-165`

### 在干什么

```python
exact_match = int(prediction.lower() == reference.lower())

pred_tokens = set(simple_tokenize(prediction))   # ← 注意 set
ref_tokens  = set(simple_tokenize(reference))
common = pred_tokens & ref_tokens
precision = len(common) / len(pred_tokens)
recall    = len(common) / len(ref_tokens)
f1 = 2 * precision * recall / (precision + recall)

rouge_scores = calculate_rouge_scores(prediction, reference)   # 3 个
bleu_scores  = calculate_bleu_scores(prediction, reference)    # 4 个
bert_scores  = calculate_bert_scores(prediction, reference)    # 3 个
meteor       = calculate_meteor_score(prediction, reference)   # 1 个
sbert        = calculate_sentence_similarity(prediction, reference)  # 1 个
# 合计 1 + 1 + 3 + 4 + 3 + 1 + 1 = 14 项
```

### 三个要点

1. **F1 用 `set()` 分词，词频被抹掉。** `simple_tokenize` 先小写、把 `. , ! ?` 换成空格、再 split。套 `set()` 后，同一词出现三次只算一次。标准 SQuAD 式 F1 用 `Counter`。**这是与论文口径的实质差异**，横向比分数时要注意。

2. **每算一条答案，`bert_score` 就单独加载推理一次**（`utils.py:71`），默认模型 `roberta-large` 约 1.4GB。199 道题就是 199 次独立前向。这是整个打分环节的时间大头，也是 8GB 显存下最容易 OOM 的地方。

3. **聚合在 `aggregate_metrics`（167-211行）**，对 `overall` 和 `category_1..5` 各算 mean/std/median/min/max。报告里**必须按类别分别给**，因为 cat4 单跳占 42%、cat5 对抗占 22%，只看 overall 会被类别比例带偏。

### 一句话记住

14 项指标全在本地算，F1 是集合版、BERTScore 是逐条调用。
