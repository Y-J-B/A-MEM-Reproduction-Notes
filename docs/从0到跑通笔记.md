## 2. 三个坑的机制

### 2.1 模型名带冒号 → `WinError 123`（❌ 必炸）

代码把模型名直接拼进路径，两处：

```python
# test_advanced_robust.py:180-183
log_filename = f"eval_robust_{model}_{backend}_ratio{ratio}_{timestamp}.log"
log_path = os.path.join(os.path.dirname(__file__), "logs", log_filename)

# test_advanced_robust.py:204-208
memories_dir = os.path.join(os.path.dirname(__file__),
                            "cached_memories_robust_{}_{}".format(backend, model))
os.makedirs(memories_dir, exist_ok=True)
```

Ollama 的模型名天生带 tag（`llama3.2:3b`），冒号在 Windows 上是**非法文件名字符**：

- 日志那一行不会立刻报错，Windows 会把 `:3b_ollama_...` 解释成 **NTFS 备用数据流**，于是你得到一个名叫 `eval_robust_llama3.2` 的 0 字节文件 —— 看起来像「跑过了但没输出」；
- 目录那一行才真炸，`OSError: [WinError 123] 文件名、目录名或卷标语法不正确`。

**规则**：`--model` 只能是 `[0-9A-Za-z._-]`。不光冒号，**花式连字符也不行**（见 2.2）。

自检（把要用的名字粘进去，输出必须是空列表）：

```powershell
& $PY -c "import sys; s=sys.argv[1]; print(repr(s), [hex(ord(c)) for c in s if not (c.isalnum() or c in '._-')])" llama32-3b
# 合格输出：'llama32-3b' []
```

### 2.2 假别名 → 每条记忆调用都失败（❌ 必炸）

上一版笔记里写的是 `llama32-3b`，但实际被输入成了 `llama32‑3b` —— 中间那个是 **U+2011（不换行连字符）**，不是 ASCII 的 `-`。看上去一模一样，Ollama 里查不到，于是：

- 目录名合法（U+2011 在 Windows 里是合法字符），所以不会报 `WinError 123`；
- 但每次 LLM 调用都打到一个不存在的模型上，日志就停在 `Creating new memories` 不动；
- 更坑的是它会在磁盘上留下一个 `cached_memories_robust_ollama_llama32‑3b` 空目录（本次就有）。

核对 Ollama 里到底有什么：

```powershell
& $PY -c "import json,urllib.request as u; print([m['name'] for m in json.load(u.urlopen('http://localhost:11434/api/tags'))['models']])"
# 必须看到 'llama32-3b:latest'
```

> Ollama 会自动补 `:latest`，**没关系**。代码用的目录名是你 `--model` 传进去的字符串，所以传 `llama32-3b` 建出来的目录就是 `cached_memories_robust_ollama_llama32-3b`，合法。

### 2.3 import 阶段卡住（⚠️ 不报错，只是慢到像死机）

`utils.py` 在**模块级**干了两件联网的事：

```python
# utils.py:22-27
nltk.download('punkt', quiet=True)
nltk.download('wordnet', quiet=True)

# utils.py:29
sentence_model = SentenceTransformer('all-MiniLM-L6-v2')
```

本机开着系统代理，实测症状：

- `huggingface.co` 的 HEAD 请求 **read timeout 10 s**，`huggingface_hub` 退避重试 **5 次**（1/2/4/8/8 s），每个文件都来一遍 → 单 `modules.json` 就要 1 分半，多文件叠加可到 10 分钟；
- `nltk` 3.10.4 有 pathsec 校验，走代理时会直接 `Security Violation: refusing a proxied fetch`，或者卡在 `_pinned_connection`；
- `litellm` 还会去拉一次 model cost map（`raw.githubusercontent.com`），90 s 后回退本地备份 —— 这条**无害**，可以不管。

**判断法**：启动后 3 分钟没有任何新日志 = 不是在算，是在等网络。别以为死了。

**解法**（✅ 已验证能把这串 HF HEAD 全部消掉）：

```powershell
$env:HF_HUB_OFFLINE = "1"
$env:TRANSFORMERS_OFFLINE = "1"
```

缓存已经完整（见第 0 节），离线模式直接读本地，一个请求都不发。

> 这条**必须在同一个终端里、启动 python 之前**设。写进系统环境变量也行，但会影响到别的项目。

## 4. 冒烟脚本（复制即用）

在项目根目录建 `smoke.py`（本文自带，不需要额外文件）：

```python
import time, sys
from test_advanced_robust import RobustAdvancedMemAgent

M = "llama32-3b"            # 必须是 Ollama 里真实存在的无冒号别名
t = time.time()
agent = RobustAdvancedMemAgent(M, "ollama", 5, 0.5)
print("agent ready %.1fs" % (time.time() - t), flush=True)

notes = [
    ("Speaker Caroline says : I went to the charity race on 8 May.", "8 May 2023"),
    ("Speaker Melanie says : My ankle was hurting after the race.", "8 May 2023"),
    ("Speaker Caroline says : We raised 2000 dollars for the shelter.", "9 May 2023"),
]
for i, (c, t2) in enumerate(notes):
    s = time.time()
    agent.add_memory(c, time=t2)
    n = list(agent.memory_system.memories.values())[-1]
    print("add#%d %.1fs kw=%s tags=%s" % (i + 1, time.time() - s, n.keywords[:3], n.tags[:2]), flush=True)

print("evo_cnt =", agent.memory_system.evo_cnt, "| memories =", len(agent.memory_system.memories), flush=True)
ctx = agent.retrieve_memory("What happened at the charity race?", k=3)
print("retrieve %d chars" % len(ctx), flush=True)
print(ctx[:300], flush=True)
```

跑：

```powershell
& $PY smoke.py
```

**验收标准**（四条全中才算通）：

1. `agent ready` 打印出来（时间可能几十秒，是在加载嵌入模型）；
2. 三条 `add#` 的 `kw=` 都**非空** —— 空列表说明模型不守格式，链路是假的；
3. `memories = 3`；
4. `retrieve` 有内容且里面能读到 charity race 相关句子。

> `evo_cnt = 0` 属正常：前两条记忆没有邻居可演化，模型判断 `NO_EVOLUTION` 也对。

## 5. 正式评测

```powershell
& $PY test_advanced_robust.py --backend ollama --model llama32-3b `
  --dataset data/locomo10.json --ratio 0.1 --retrieve_k 10 `
  --output results_smoke.json
```

| 参数 | 含义 | 这里的取值理由 |
|---|---|---|
| `--backend ollama` | LLM 后端 | 本地推理，零成本 |
| `--model llama32-3b` | 模型名 | **无冒号 ASCII 别名**，否则 `WinError 123` |
| `--ratio 0.1` | 数据比例 | 10 个对话 ×0.1 = **1 个完整对话**（588 turn，约 199 题）。它不是「题量比例」 |
| `--retrieve_k 10` | 检索条数 | 与论文默认一致；缓存建好后改 k 只重跑答题，很便宜 |
| `--output` | 结果文件 | 落在项目根目录 |

另开一个终端盯进度：

```powershell
Get-Content logs\eval_robust_llama32-3b_ollama_ratio0.1_*.log -Wait -Tail 20
```

### 5.1 耗时账（按实测 85 tok/s 推）

| 阶段 | 量 | 估算 |
|---|---|---|
| 建库 | 588 turn，每 turn 至少 1 次调用、平均约 2 次 | 1200 次左右 × 6–10 s ≈ **2–3 小时** |
| 答题 | 199 题 × 2 次调用 | ≈ **40–60 分钟** |
| BERTScore 打分 | 199 次独立前向（roberta-large） | 额外 10–20 分钟，且内存峰值最高 |

### 5.2 断点续跑：只在「整段对话建完」之后才成立

`memory_cache_sample_0.pkl` 是在**这个样本 588 轮全部灌完**后才 `pickle.dump` 的（`test_advanced_robust.py:237-240`）。所以：

- 建库中途 Ctrl+C → **缓存不落盘，下次从头再来**；
- 答题中途中断 → 缓存已在，重跑只重答，几十分钟能补完。

这决定了现实策略：**要么让它一次跑完 2–3 小时，要么先把 turn 数砍下来**。

## 6. 想让「跑通」更快：三条路，按推荐度排

1. **砍 turn 数（最有效）**：复制 `data/locomo10.json` 成 `data/locomo_mini.json`，只留第 1 个样本、每个 session 保留前 3–5 轮、`qa` 留 20 题。588 → 40 轮，建库 5–8 分钟，全链路 20 分钟内出分。⚠️ 这类子集分数**只能证明链路通**，不能写进报告的横向比较。
2. **换 `llama3.2:1b`**：速度快 2–3 倍，但格式服从性差，会触发 `Keywords empty after initial parse` 的 fallback 重试，**总时间不一定更短**，且分数更低。
3. **别砍题**：题只占 1/3 时间，砍题收益小，还会让 category 分布变得没法解释。

## 7. 看结果与报告口径

```powershell
& $PY -c "import json; r=json.load(open('results_smoke.json',encoding='utf-8')); print('题数:', r['total_questions']); print('分布:', r['category_distribution']); [print(s, 'F1=%.4f BLEU1=%.4f' % (m['f1']['mean'], m['bleu1']['mean'])) for s, m in r['aggregate_metrics'].items()]"
```

- 只有 `f1` 和 `bleu1` 当主指标，其余 12 项作辅助（`utils.py:109-165` 共 14 项）；
- **按类别分别给**：cat4 单跳占 42%、cat5 对抗占 22%，只看 overall 会被类别比例带偏；
- **不要报 `exact_match`**：严格全字符串匹配，LoCoMo 短答案下几乎恒为 0，没有解释力；
- **绝对不要写没跑出来的分数**。仓库里至今没有任何历史结果文件，任何「论文说 a-mem 能到 xx」都不算你的实验结果。
